# Contributing

Read [`PRODUCT_SPEC.md`](PRODUCT_SPEC.md) first. Its requirement identifiers (`LIB-003`,
`PLAY-004`, …) are contractual and are referenced from code, tests, commits and pull requests.

## Prerequisites

`./gradlew verifyDebug` needs a JDK and an Android SDK. CI installs both through its setup actions,
so a fresh clone can fail with errors that look like a broken build rather than a missing toolchain.

- **JDK 17 or newer.** The build targets JVM 17.
- **Android SDK** with `platforms;android-36` and `build-tools;36.0.0` — the levels pinned in
  `gradle/libs.versions.toml`. Bumping those pins means installing the matching packages.
- **`local.properties`** in the repository root pointing at the SDK. It is gitignored, because the
  path is specific to your machine:

  ```properties
  sdk.dir=/path/to/android-sdk
  ```

  Setting `ANDROID_HOME` works instead, if you prefer not to have the file.

From nothing, on Linux:

```bash
# Command-line tools, then the packages the build needs.
sdkmanager --licenses
sdkmanager "platform-tools" "platforms;android-36" "build-tools;36.0.0"
echo "sdk.dir=$ANDROID_HOME" > local.properties
```

A cold first build resolves the whole dependency graph and takes several minutes; subsequent runs are
around five. If Gradle cannot reach `dl.google.com` — the host serving both Google's Maven repository
and the SDK — nothing will resolve, and the failure will not name the network as the cause.

## The loop

1. **Identify the requirement IDs** your change implements.
2. **Read what exists.** The relevant `PRODUCT_SPEC` section, the ADRs in `docs/adr/`, and
   `docs/api-compatibility.md` for anything touching the server. Search for an existing
   implementation before creating a parallel abstraction.
3. **Identify the tests that prove current behavior**, so you can tell whether you changed it.
4. **Write tests or fixtures first** for policy and API changes.
5. **Implement the smallest vertical slice** that satisfies the acceptance criteria.
6. `./gradlew ktlintFormat`
7. `./gradlew verifyDebug` — never mark work complete while this fails.
8. **Update the docs**: architecture notes, the compatibility matrix, an ADR if you changed a
   boundary or a rule.
9. **State your assumptions in the pull request**, not as hidden behavior in code.

## Hard rules

These come from `PRODUCT_SPEC 16.3`, `22` and `CLAUDE.md`. They are enforced by detekt and Android
Lint where a tool can enforce them, and by review where one cannot.

- No direct API calls from a Composable or a ViewModel. Go through a use case or repository.
- No `GlobalScope`. Use `@ApplicationScope`, `viewModelScope` or a service scope.
- No raw `Dispatchers.*` outside `CoroutineModule`. Inject `@Dispatcher(...)`.
- No `System.currentTimeMillis()` in domain logic. Inject `AppClock`.
- No swallowed exceptions, no empty catch blocks, and no broad `catch (Throwable)` outside
  `resultOf`. Cancellation is always rethrown.
- No generic `Exception` across a layer boundary. Return `AppResult` with a typed `AppError`.
- Exhaustive `when` on sealed domain types — no `else` branch.
- No mutable `Flow` exposed from a class.
- No dynamic dependency versions, no `+`, no unpinned Git dependencies.
- No destructive Room migration, ever. `fallbackToDestructiveMigration` must not appear.
- No TLS bypass, no trust-all mode, no certificate pinning by default.
- No token in a URL generated by app code.
- No `TODO` without a tracked issue reference: `TODO(#123): …`.
- Never claim that the Audiobookshelf database-delete endpoint deletes media files.
- No official Audiobookshelf branding, and no code copied from the GPL application without a
  recorded licensing decision.

## Logging

Every log call goes through `Logger` with structured `LogField`s. The message must be a **constant**
string; anything variable belongs in a field, because only fields pass through the redactor. Reviewers
should treat an interpolated log message as a defect.

Pick the field type that matches the value: `Secret`, `ServerHost`, `Username`, `MediaTitle`,
`FilePath`, `Url` and `Identifier` all redact; `Public`, `Count` and `Millis` do not. See
[ADR-0004](docs/adr/0004-redacted-structured-logging.md).

## Tests

`PRODUCT_SPEC 17.1` says where a test belongs. Prefer hand-written fakes with real state over mocks.
Use Robolectric only where the subject is genuinely Android or SQL behavior. Never add a test that
only raises a coverage number — `PRODUCT_SPEC 17.3` says coverage is a signal, not permission.

## Pull requests

Small, and each one names its requirement IDs. `PRODUCT_SPEC 18` requires: main is always buildable,
no merge with failing checks, an ADR for an architecture change, a migration test for every database
version bump, and an explanation for any API fixture change.

## Definition of Done

`PRODUCT_SPEC 21`, in full. A feature is not done with only a happy-path screen: error, loading,
empty, offline and permission states, accessibility semantics, no private data in logs, migrations or
fixtures included, docs updated, destructive wording reviewed, playback regression considered.
