# Security

## Reporting a vulnerability

Use GitHub's private vulnerability reporting on this repository. Please do not open a public issue
for a security problem.

Include what you did, what happened, and what you expected. If the report involves a self-hosted
server, please redact its hostname — this project's own diagnostics do the same by default, and we do
not want your server address either.

## Invariants

These come from `PRODUCT_SPEC 15` — the lock group from the sentences `docs/gaps.md` collects as
`AUTH-005` — and must not regress. A change that weakens one needs an ADR and an explicit review, not a
commit message.

**Transport**

- HTTPS by default. Release builds reject cleartext (`app/src/main/res/xml/network_security_config.xml`).
- Platform certificate trust only. There is no `sslSocketFactory` override, no custom
  `HostnameVerifier`, and no "trust all certificates" mode anywhere in this repository — including in
  debug builds, where such a switch is usually added and then forgotten.
- No certificate pinning by default: self-hosted certificates rotate, and pinning locks users out.
- A future custom-CA feature must use explicit certificate import and show the fingerprint.

**Credentials**

- Passwords are never persisted.
- Tokens are encrypted with Android Keystore-backed key material (`AUTH-003`). The database contains no
  raw tokens, and `AuthToken.toString()` is overridden so that interpolating the object holding one
  cannot print it.
- **`GET /api/users` returns every user's live token.** The app must never model that field: `UserDto`
  and `UserSummaryDto` have no `token` property, so there is nothing to store, log or display. Pinned by
  `CapturedShapesTest` — this is an invariant about a *response shape*, and the only way to keep it is to
  refuse to parse the field.
- Authorization is a header, never a query parameter generated by app code.
- Backup and device transfer are fully excluded (`app/src/main/res/xml/data_extraction_rules.xml`), so
  a restore cannot carry a token to another device or leave an undecryptable state.

**Profile lock**

What this lock defends is which account this device shows, against somebody holding the already-unlocked
phone who is not the account's owner. That threat, and everything below that follows from it, is written
down in [ADR-0023](docs/adr/0023-the-profile-passcode-is-a-curtain-not-a-vault.md) (`AUTH-005`).

- Passcodes are never persisted, for the same reason passwords are not. A record holds a
  PBKDF2-HMAC-SHA256 verifier over a salt generated per record, at 210,000 iterations, compared with
  `MessageDigest.isEqual`, and the record is encrypted with AES-256-GCM under a non-extractable Keystore
  key.
- The lock's Keystore alias is `shelfplayer.lock.v1` and its directory is `locks/`, deliberately **not**
  the session alias and not `sessions/`. Sharing either would have made `SessionTokenStore.clear` delete a
  passcode on sign-out, `clearAll()` destroy the verifier's key — which fails closed, so signing out of
  everything would lock the app permanently — and `storedCredentialCount()` report a lock as a stored
  credential.
- **A six-digit passcode behind a KDF does not resist an attacker who is holding the file.** A million
  possibilities at 210,000 iterations is roughly 2 × 10^11 hash iterations, which one modern GPU exhausts
  in minutes. What the Keystore wrap buys is exactly one property — obtaining the record requires
  executing code on this device rather than copying a file off it — and no claim past that sentence may
  be made for it, here or in the product (`docs/risks.md` R-40).
- Every failure to read, unwrap or parse a record resolves to *locked*, never to *no passcode*. This is
  why the record is a proto of its own: `AppSettingsDataSource.settings` catches `IOException` and emits
  `getDefaultInstance()`, which is correct for a preference and **fail-open** for a lock.
- The rate limit — four free attempts, then thirty seconds doubling to a fifteen-minute cap, and refusal
  at ten — lives inside the encrypted record, so force-stopping the app or clearing its data cannot reset
  it. It binds the only attacker this design is for, the one who goes through the app.
- **Biometric unlock is app-enforced policy and not cryptography.** The verifier is a one-way derivation,
  so no fingerprint can produce it: the gateway asks the platform, trusts the answer and grants an
  in-memory ticket. That is weaker than a key a biometric releases, and it is the only shape available
  when the stored value is a hash by design.
- **The device credential is deliberately not an unlock factor.**
  `KeyguardManager.createConfirmDeviceCredentialIntent` is the obvious fallback and is refused, because
  the threat is somebody holding the already-unlocked phone and that person has the device credential by
  construction. The record's key sets `setUserAuthenticationRequired(false)` for the same reason:
  requiring device authentication in order to check a passcode would be circular as well as useless.
- The bypasses that exist are disclosed on the lock curtain itself rather than only here — the media
  notification and lock-screen transport keep working, because this app has no interception point for a
  media button and `ROUTE-001` treats one as explicit intent; a connected car can still browse and play;
  downloaded audio is ordinary unencrypted files; and the lock does nothing against somebody who can read
  the phone's files. Nothing suppresses the app-switcher thumbnail on any API level either, which is
  recorded in `docs/gaps.md` and is not on that screen.
- Recovery from a forgotten passcode is signing in to the account again, which clears the record
  (`SignInUseCase` calls `LockedProfileRecovery`, and only for a profile that is actually locked, so an
  ordinary `AUTH-004` re-authentication does not switch somebody's lock off). It is a higher bar than six
  digits rather than a bypass, and its cost is stated before the passcode is set: it needs the server, so
  it is no help offline.

**Logging and diagnostics**

- Tokens, cookies, passwords, hosts, usernames, media titles, descriptions and filesystem paths are
  redacted by default. See [ADR-0004](docs/adr/0004-redacted-structured-logging.md).
- Exception messages are never logged — only the exception-class chain — because
  `UnknownHostException`'s message is the hostname.
- No analytics and no crash reporting. Any future crash reporting is opt-in and strips private
  content.

**Destructive actions**

- `Remove from Audiobookshelf database` and `Delete source files` are separate operations with
  separate capabilities. The database-delete endpoint does not delete files, and no UI may say it
  does (`MGR-005`, `MGR-006`, `PRODUCT_SPEC 22.12`).
- **True source-file deletion ships no feature at all**, and that is a decision rather than an omission.
  `MGR-006` requires a server response that explicitly confirms the deletion; Audiobookshelf logs a
  failed filesystem removal server-side and discards it, so the request succeeds either way and no
  capture can distinguish the two. [ADR-0021](docs/adr/0021-source-file-deletion-ships-no-feature.md)
  records the reasoning and `ManagementActionTest` guards it.
- **Embedding metadata rewrites the user's source audio files** (`MGR-007`). One item at a time, never
  the batch endpoint, and always with the server's own backup requested — never a toggle. A mis-tap that
  rewrites one book is recoverable; one that rewrites a library may not be.

**Build**

- Every dependency version is pinned; repositories are restricted and content-filtered.
- Dependency verification is **strict**, over 890 pinned components with SHA-256 checksums generated
  against the resolved version set. An artifact whose checksum is absent or wrong fails the build rather
  than warning. `verify-signatures` stays false because several AndroidX and Google artifacts are
  unsigned; see [ADR-0006](docs/adr/0006-dependency-locking-and-verification.md).
- CI validates the Gradle wrapper and scans for secrets on every pull request.
- No production secrets in the repository. There is no signing configuration.

## Supported versions

**Still pre-release: no version is supported for security updates yet.** What has changed is that the
reasons are no longer open questions. ADR-0024 settled the licence as **GPL-3.0-or-later** and the channel
as **Google Play**, so the route by which a fix would reach anybody now exists on paper.

What that means for this section once there is a first release:

- **The latest release on Google Play is the supported version, and only that one.** A single-maintainer
  project cannot honestly promise backports, and Play's staged rollout is the delivery mechanism.
- **Fixes ship as a new `versionCode`.** Play requires a strictly increasing integer and never permits
  reuse, so there is no such thing as re-issuing a version in place.
- **Building from source is always available**, which GPL-3.0 guarantees and which is the fallback for
  anybody who does not want the store's copy.

Nothing above is in force yet, because there is no release. It is written now so that the first release
does not have to invent a policy in a hurry.

## What has not been verified

Stated because an invariant nobody has tested is a claim, not a guarantee. The transport, credential and
logging invariants above are enforced by tests that run on every pull request. These are not:

- **No instrumented test exists.** The whole UI tier is Robolectric on the JVM at API 34; `minSdk` is 26.
- **The release build is assembled but never launched**, so R8's effect on reflection-shaped code —
  Room, Hilt, Media3, serialization — is unexercised.
- **Two of the management contracts are derived from the server's source rather than captured**, because
  they need permissions the public demo account does not hold: cover upload and embed metadata.
- **The profile lock's platform half is exercised by nothing.** The Keystore wrap cannot run under
  Robolectric, which has no `AndroidKeyStore` provider, and a biometric prompt is a window the system
  draws, so neither is reachable without a device (`docs/risks.md` R-39). What *is* covered, on the JVM:
  the derivation and its passcode policy, the gate's clock arithmetic, `ROUTE-002`'s truth table, the
  process-lifecycle wiring that makes the relock delay fire at all, the curtain under Robolectric —
  including the disclosure block, which is asserted line by line so this feature's honesty cannot be
  deleted without a red build — and the profile switcher's passcode prompt.
- **Nothing about the lock has been seen by a person.** No passcode has been typed on hardware and no
  biometric prompt has ever been drawn by this app.

`docs/risks.md` carries the full accounting, with the cheapest thing that would retire each one.
